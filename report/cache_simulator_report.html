Abstract

In modern computer systems, the performance of microprocessors is largely constrained by the memory wall—the latency disparity between processor registers and dynamic random-access memory (DRAM). Cache memory mitigates this bottleneck by exploiting temporal and spatial locality. This project presents a full-featured, academic Cache Memory Simulator engineered with a C++17 algorithmic core, an asynchronous Python Flask REST backend, and a modern single-page browser frontend.

The system accurately implements Direct Mapping, Fully Associative Mapping, and N-Way Set Associative Mapping, paired with FIFO and LRU eviction policies. It features comprehensive 32-bit address decomposition into Tag, Index/Set, and Block Offset fields, dynamic performance metrics calculation, step-by-step state reconstruction, and 90 automated validation tests.

1. Introduction & Theoretical Foundations

1.1 Memory Hierarchy

Computer memory is organized hierarchically to balance high speed and low storage cost per bit:

  • Registers: Inside CPU, single-cycle access latency (< 0.5 ns), capacity < 1 KB.
  • L1 Cache: On-core SRAM, ~1 ns latency, capacity 32–64 KB.
  • L2 Cache: Dedicated per-core SRAM, ~4–10 ns latency, capacity 256 KB–4 MB.
  • L3 Cache: Shared multicore SRAM, ~20–40 ns latency, capacity 8–64 MB.
  • Main Memory (DRAM): Synchronous DRAM, ~60–100 ns latency, capacity 8–128 GB.
  • Secondary Storage: NVMe SSD / HDD, latency in microseconds to milliseconds.

1.2 Locality of Reference

The efficacy of caching relies on two empirical behavioral properties of computer programs:

Temporal Locality: A memory address referenced at time t is likely to be referenced again in the near future (e.g., loop counters, hot functions).
Spatial Locality: If memory address A is referenced, adjacent addresses (A + 1, A + 2, ...) will likely be referenced soon (e.g., sequential instruction execution, array traversal).

4. Algorithmic Implementation

4.1 C++17 Direct Mapping Logic

SimEvent DirectMappedCache::access(uint32_t address) {
    ++stats.total_accesses;
    auto bd = breakdown_address(address, cfg);
    SimEvent ev;
    ev.address = address;
    ev.block_number = bd.block_number;
    ev.tag = bd.tag;
    ev.index = bd.index;
    ev.offset = bd.offset;

    CacheLine& line = lines[bd.index];
    if (line.valid && line.tag == bd.tag) {
        ev.hit = true;
        ev.event_type = "HIT";
        ++stats.hits;
    } else {
        ev.hit = false;
        ++stats.misses;
        if (line.valid) {
            ev.replacement = true;
            ev.victim_line = bd.index;
            ev.evicted_block = line.block;
            ev.event_type = "MISS_REPLACE";
        } else {
            ev.event_type = "MISS";
        }
        line.valid = true;
        line.tag = bd.tag;
        line.block = bd.block_number;
    }
    return ev;
}

6. Viva Voce Preparation Guide

Q1: Why must the block size and cache size be powers of two?
A: In binary byte-addressable architecture, powers of two allow address decomposition via direct bit-slicing (shifts and masks) rather than expensive hardware division circuits.
Q2: Why doesn't a cache hit update the FIFO queue?
A: First-In First-Out (FIFO) replacement strictly tracks the order of arrival (insertion) into the cache, irrespective of how many times a block is referenced. Updating recency on hits is the defining characteristic of Least Recently Used (LRU).
Q3: What are the three types of cache misses (the 3 Cs)?
A: 1. Compulsory Misses (Cold): First reference to a memory block.
2. Capacity Misses: Cache cannot contain all blocks needed for program execution.
3. Conflict Misses (Collision): Occurs in direct-mapped or set-associative caches when multiple blocks map to the same line/set despite empty slots elsewhere.
